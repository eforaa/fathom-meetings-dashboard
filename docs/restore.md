# Как восстановить базу из копии

Копия собирается каждую ночь в 03:00 и лежит в хранилище того же проекта
Supabase, в разделе `backups`. Хранятся последние семь.

Эта процедура **отрепетирована на живых данных** 27 августа 2026: строка
журнала была удалена из базы и возвращена из копии — вернулась целиком,
поле в поле.

---

## Сначала посмотреть, ничего не трогая

```bash
node tools/restore.mjs
```

Инструмент по умолчанию **ничего не пишет**. Он берёт последнюю копию,
разбирает её и печатает:

- сколько строк в каждой таблице;
- битые строки, если они есть, — с номерами;
- ссылаются ли участники на встречи, которых в копии нет;
- **чем копия отличается от нынешней базы**: совпало / изменилось / нет в базе.

Строка «нет в базе N» — это и есть то, что потерялось. Ноль во всех трёх
столбцах означает, что база и копия совпадают и восстанавливать нечего.

## Взять другую копию

```bash
node tools/restore.mjs --file=2026-08-26-03-00.ndjson.gz
```

Имена — это дата и время сбора. Список всех копий инструмент печатает первой
строкой.

## Восстановить

```bash
node tools/restore.mjs --write
```

Запись идёт `upsert`-ом: строка узнаётся по ключу и обновляется, а не
добавляется второй раз. Поэтому запускать можно сколько угодно раз подряд —
данные не размножатся.

Порядок таблиц соблюдается сам: аккаунты и колонки, потом встречи, потом
участники. Обратный порядок упёрся бы во внешний ключ.

## Восстановить одну таблицу

```bash
node tools/restore.mjs --write --only=meetings
```

Полезно, когда пострадало что-то одно: не трогаем остальное.

---

## Чего в копии нет и почему

**Расшифровок.** Они весят 45 МБ, и запрос за ними не укладывается в минуту,
отведённую Vercel. Но главное — они единственное, что можно взять заново:
расшифровки лежат в Fathom, и повторная синхронизация притащит их обратно.
Полная копия с расшифровками собирается вручную:

```
POST /api/cron/backup?transcripts=1
```

**Служебной колонки поиска.** База вычисляет её сама из остальных полей.

**Зашифрованного ключа Fathom.** Восстановиться без него — минута: вставить
ключ заново на странице настроек. Файл с ключами в том же хранилище стоил бы
дороже.

---

## Что делать, если копия не читается

Инструмент назовёт номера битых строк и продолжит с остальными — файл
построчный, одна испорченная строка не уносит весь. Если испорчено много,
возьмите предыдущую копию: их семь.

## Если база потеряна целиком

1. Поднять новый проект Supabase.
2. Применить `db/apply-all.sql` — он создаёт таблицы и индексы.
3. Прописать новые `SUPABASE_URL` и `SUPABASE_SERVICE_KEY`.
4. `node tools/restore.mjs --write`.
5. На странице настроек вставить ключ Fathom заново.
6. Запустить синхронизацию — расшифровки подтянутся из Fathom.

Шаг 2 сегодня неполный: `db/` описывает не все колонки, часть создавалась
руками. Это отдельная задача, и пока она не сделана, восстановление «с нуля»
потребует ручной доводки схемы.
